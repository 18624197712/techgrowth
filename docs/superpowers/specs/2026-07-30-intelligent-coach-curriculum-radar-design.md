# TechGrowth 智能导师、课程体系与每日雷达设计

## 目标

把当前只有固定回复、通用任务模板和种子雷达数据的实现，升级为可验证的个人技术成长闭环：每天获取新技术信号，依据长期课程路线与真实证据生成一个具体任务，再由能够识别意图的上下文导师提供辅导。

## 范围

本次交付包含三个相互衔接的子系统：

1. 具备意图识别、相关上下文选择和写操作确认的智能导师。
2. 覆盖 AI/LLM 工程、后端与架构、工程质量、云与 DevOps 的体系化每日任务。
3. 每天 08:00（Asia/Shanghai）运行、可观察且允许手动补跑的技术雷达。

不包含多用户协作、任意工具调用、自动执行仓库代码、自动修改技能等级或未经确认执行写操作。

## 课程体系

### 轨道与阶段

课程目录由版本化的代码配置维护，避免模型临时发明学习路线。四条轨道的目标占比为：

| 轨道 | 权重 | 阶段 |
| --- | ---: | --- |
| AI/LLM 工程 | 40% | 基础、实战、生产化、架构 |
| 后端与架构 | 25% | 基础、实战、生产化、架构 |
| 工程质量 | 20% | 基础、实战、生产化、架构 |
| 云与 DevOps | 15% | 基础、实战、生产化、架构 |

每个阶段至少定义三个有序技能节点，共提供至少 48 个节点。节点包含稳定 ID、名称、前置节点、学习目标、推荐产物、验收类型和检索关键词。课程版本写入任务，后续升级目录不会改变旧任务的含义。

### 每日节点选择

选择器只使用确定性规则，模型不能决定用户是否晋级：

1. 未通过的补做任务优先于新任务。
2. 过滤前置节点尚未通过的候选节点。
3. 在最近十个非补做任务的滑动窗口中，选择最偏离 40/25/20/15 目标占比的轨道。
4. 在该轨道中选择最早未通过、证据最弱的节点。
5. 14 天内不重复同一节点；补做任务不受此限制。

节点只有在关联提交通过 Rubric 审阅并生成成长证据后才视为完成。模型输出不能直接修改技能等级或课程进度。

### 具体任务契约

`LearningTask` 在保持旧字段兼容的基础上新增：

- `curriculum_version`、`track_key`、`stage_key`、`node_key`
- `prerequisites`：开始前必须具备的知识或环境
- `instructions`：3 至 6 个步骤，每步包含动作、预计分钟数和可观察结果
- `deliverables`：必须提交的文件、Commit、答案或报告
- `acceptance_checks`：可执行命令或人工检查，以及明确预期结果
- `rubric`：2 至 5 项，每项包含说明、是否关键项及 0–4 分锚点
- `remediation_hint`：未通过时聚焦补做的规则

任务总时长必须为 30–45 分钟，步骤分钟数之和必须落在同一范围；必须至少有一个产物、两个验收检查、一个关键 Rubric 项和一个有效来源引用。Pydantic 与领域策略同时校验这些约束。模型输出连续失败时，使用当前课程节点的具体模板生成合规任务，不返回现有的三条通用文案。

## 技术雷达

### 调度与数据流

Worker 使用 `Asia/Shanghai` 时区的 Cron 调度：

- 08:00 抓取 OpenAI、Hugging Face、目标 GitHub Releases、arXiv 与 Hacker News。
- 08:10 在雷达任务结束后生成今日任务。
- 若 08:00 抓取仍在运行，08:10 任务等待本次抓取完成，但最长等待两分钟；超时或失败后使用历史数据和课程目录继续生成。

手动刷新复用同一抓取服务和互斥锁。相同日期的自动补跑、容器重启和手动点击均保持幂等，不产生重复条目。

### 处理规则

抓取结果依次进行规范 URL、来源键、标题指纹去重；过滤缺少链接的条目并保留来源、发布时间和引用摘要。Embedding 使用独立 Embedding Base URL、模型和 API Key。相关性由课程关键词、当前技能短板、内容向量相似度和来源可信度共同计算，雷达只能影响当前课程节点的技术背景，不能跳过课程前置条件。

单个来源失败不会阻塞其他来源。全部来源失败时保留历史雷达数据。每次运行写入 `AgentRun`，记录开始/结束状态、成功来源数、失败来源及脱敏错误、新增条目数和引用 ID。雷达页面展示最近抓取时间和这些统计，并提供“立即刷新”按钮。

## 智能导师

### 工作流

`ChatWorkflowService` 使用有边界的 LangGraph：

1. `classify_intent` 输出受 Pydantic 校验的 `ChatIntentDecision`。
2. `authorize` 判断请求是只读回答还是写操作提议。
3. `load_context` 仅加载该意图需要的数据。
4. `answer` 使用 Chat 服务生成中文回答。
5. `propose_action` 对允许的写操作创建一次性待确认操作。

支持的意图为：`technical_qa`、`task_coaching`、`submission_improvement`、`growth_planning`、`radar_to_task`。低置信度分类回退到 `technical_qa`，并在回答中询问必要信息，不猜测写操作。

### 上下文与安全

上下文可以包含当前页面标识、今日任务、Rubric、相关提交与审阅摘要、技能画像、课程进度和相关雷达条目。每类意图使用白名单字段，限制记录数量与总字符数，并把仓库、雷达和用户提交内容标为不可信数据。绝不发送 API Key、TOTP、恢复码、Session、设备私钥或通知凭据。

API 每次请求从加密数据库读取最新的 Chat 配置，并使用与 Worker 相同的 provider 解析规则。模型未配置、401/403、429、超时、Schema 错误和内容解析错误必须映射为可读错误事件，不能返回固定成功文案。

### 流式协议与确认操作

`POST /chat/stream` 返回以下 SSE 事件：

- `intent`：意图、置信度和只读/待确认状态。
- `token`：回答文本片段。
- `action_proposal`：操作 ID、摘要和过期时间。
- `error`：稳定错误码和中文信息。
- `done`：本轮结束。

第一版允许的写操作只有“由雷达条目创建课程兼容任务”。服务端保存带过期时间的操作提议，`POST /chat/actions/{id}/confirm` 在 CSRF 校验后执行一次；重复确认保持幂等，过期或非本人会话的操作拒绝执行。导师侧栏显示识别意图、流式回答、确认或取消按钮及失败状态。

## 数据与迁移

使用向后兼容 Alembic 迁移扩展 `learning_tasks` 的课程、产物和验收字段，并为旧任务填入安全默认值。新增待确认操作表；`agent_runs` 增加结构化运行详情字段，用于雷达状态。现有 Provider 密钥、旧任务、证据和雷达条目不得丢失，部署迁移必须能够在旧 API 镜像仍运行时完成。

## 错误处理与可观察性

- 所有模型调用设置超时、token 上限和有限重试，并记录不含消息正文和密钥的 `AgentRun`。
- SSE 在响应开始后发生错误时发送 `error` 与 `done`；响应开始前的鉴权和输入错误继续使用 HTTP 状态码。
- 雷达来源错误按来源隔离，页面可见最近一次运行结果。
- 任务生成失败不会创建半成品记录；只有完整 Schema 和领域策略均通过后才提交事务。
- Worker 重启后的同日补跑基于运行日期和任务唯一性判断，不重复抓取运行或每日任务。

## 测试与验收

### 单元测试

- 四轨权重选择、前置节点、证据晋级、14 天不重复和补做优先级。
- 具体任务的时长、步骤、产物、验收检查、Rubric 锚点和引用约束。
- 五类意图分类、低置信度回退、上下文字段白名单和敏感字段排除。
- 雷达调度时间、去重、部分失败、全部失败和同日幂等。

### 集成测试

- 使用固定 OpenAI 兼容假服务验证 Chat 与 Embedding 使用各自 Base URL、模型和 API Key。
- 验证 SSE 事件顺序、模型错误事件、操作提议确认、过期和重复确认。
- 验证 08:00 雷达结果能够被 08:10 的课程任务引用，雷达失败时仍生成合规任务。

### Web 与生产验收

- Playwright 覆盖意图标签、流式回复、错误展示、操作确认、任务详细字段、雷达运行状态和手动刷新。
- 生产部署前运行 API、Web、Connector 全量测试和构建。
- 部署后在备案域名验证模型真实回答、至少三类意图、一次确认操作、雷达手动刷新、调度的下一运行时间及 Worker 健康状态。

## 发布顺序

1. 数据迁移与课程领域规则。
2. 体系化任务生成与页面展示。
3. 雷达运行记录、08:00 调度和手动刷新。
4. 智能导师工作流、SSE 协议与操作确认。
5. 全量回归、备份、推送主分支和 ECS 滚动部署。
